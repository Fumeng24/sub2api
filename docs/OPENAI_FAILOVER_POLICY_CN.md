# OpenAI 上游自动切号策略（讨论稿）

本文记录 OpenAI `/responses` 链路遇到上游错误时的自动切号策略，重点处理用户反馈的“请求失败但看起来仍在计费”问题。

## 背景

用户反馈在调用 `/responses` 流式接口时出现频繁重连、`502`，并认为失败请求仍然扣费。

排查结论：

- 真正返回 `502` 的失败请求没有写入 `usage_logs`，也没有产生计费记录。
- 部分请求会先遇到某个上游账号超时或失败，再自动切到其他账号成功；这类请求会在 `ops_error_logs` 中记录 `Recovered upstream error`，同时因为最终成功完成而正常计费。
- 用户侧看到“重连/失败提示”和后续成功扣费挨得很近，容易理解成“失败也扣费”。
- 问题集中在异常上游账号仍被调度，例如某账号持续出现 `502`/timeout 但仍处于 `active`、`schedulable=true`。

## 当前行为

当前 OpenAI `/responses` handler 已经具备部分自动切号能力：

- 上游连接失败、请求超时、流式响应开始前断流，会抛出 `UpstreamFailoverError`，handler 会排除当前账号并选择下一个账号。
- 上游错误被切号恢复后，最终请求成功，会记录成功用量；同时 `ops_error_logs` 会记录一条 `Recovered upstream error` 便于运维观察。
- 流式响应已经向客户端输出后，不再安全切号，因为新账号无法接续旧账号已经输出的 SSE 流。

当前实现：

- `/responses` passthrough 分支对上游 HTTP 错误已支持 `429`、`502`、`503`、`504`、`529` 的自动切号。
- 自动切号只发生在服务端尚未向客户端写出响应前。

## 拟调整策略

### 自动切号状态码

对 `/responses` passthrough 上游 HTTP 响应，在响应尚未写给客户端前，以下状态码会触发自动切号：

| 状态码 | 含义 | 策略 |
| --- | --- | --- |
| `429` | 上游限流 | 自动切号，保持现有行为 |
| `502` | 上游网关/代理错误 | 自动切号，并记录账号失败 |
| `503` | 上游服务不可用或过载 | 自动切号，并对账号做短暂冷却 |
| `504` | 上游超时 | 自动切号，并对账号做短暂冷却 |
| `529` | 上游过载 | 自动切号，并按过载处理 |

暂不扩大到：

| 状态码 | 原因 |
| --- | --- |
| `400` | 多数是请求格式、上下文或模型参数问题，盲目切号可能污染其他账号 |
| `401` | 可能是账号凭证失效，应进入账号异常处理，不应简单无限切号 |
| `403` | 可能是账号权限、模型权限或用户请求策略问题，需要单独判定 |
| `408` | 可后续评估；需要区分客户端上传中断和上游超时 |

### 流式安全边界

自动切号只允许发生在服务端尚未向客户端写出响应前。

如果 SSE 已经开始输出：

- 不强行切号。
- 记录上游错误和上下文。
- 保持当前流式错误处理，避免客户端收到半截旧流加半截新流。

原因：不同上游账号无法保证同一请求的 token、tool call、response id、usage 和状态机可以无缝接续。

### 异常账号冷却

对 `502`、`503`、`504`、`529` 触发 failover 的账号，会进入调度失败统计。

建议规则：

- 单账号在短窗口内连续出现同类 transient 错误，写入 `temp_unschedulable_until`。
- 默认冷却时间可从 `10` 分钟起步。
- 冷却结束后允许少量探测流量，成功后恢复正常调度。
- 冷却原因写入 `temp_unschedulable_reason`，便于后台展示。

目标是避免每个用户请求都先踩同一个坏账号。

## 告警指标与参数建议

基于最近一段历史错误分布（`2026-06-20` 到 `2026-06-28`）：

- `38805` 的连续 5xx 高峰可达到 5 分钟内 `292` 次，连续 burst 最长约 `814s`。
- `38850` 的连续 5xx 高峰可达到 5 分钟内 `242` 次，连续 burst 最长约 `1559s`。
- 账号级 transient 5xx 在 5 分钟窗口下，`attempts>=10 && 5xx>=5 && error_rate>=50%` 可以覆盖约 `48%` 的 5xx。
- 同样口径放宽到 `attempts>=5 && 5xx>=3 && error_rate>=50%` 可以覆盖约 `57%` 的 5xx，但窗口数和账号数会明显变多。

建议拆成两层：

### 1) 告警指标

| 指标 | 口径 | 用途 |
| --- | --- | --- |
| `openai_account_5xx_count` | 5 分钟窗口内 `502/503/504/529` 数量 | 账号健康告警 |
| `openai_account_5xx_rate` | `transient_5xx / attempts`，`attempts = 5xx + success + recovered` | 过滤偶发毛刺 |
| `openai_account_5xx_burst` | 连续 5xx burst 长度 | 发现长时间不稳定上游 |

### 2) 推荐阈值

| 层级 | 窗口 | 阈值 | 说明 |
| --- | --- | --- | --- |
| 软告警 | 5 分钟 | `attempts >= 10 && transient_5xx >= 5 && rate >= 0.5` | 适合先做告警/观察 |
| 自动冷却 | 60 秒 | `transient_5xx >= 3` | 适合快速止损，冷却后再探测 |
| 加重冷却 | 5 分钟 | `attempts >= 20 && transient_5xx >= 10 && rate >= 0.5` | 对明显坏号直接拉长冷却 |

### 3) 冷却参数

当前代码复用了现有的账号临时不可调度路径，相关参数还没有独立抽成新的 `openai_account_5xx_*` 配置项。

建议初始值仍按下面口径执行：

- `window_seconds=60` 用于快速拦截短时 burst。
- `threshold=3` 是为了在 1 分钟内连续多次 5xx 时尽快熔断。
- `cooldown_seconds=30` 先做短冷却，避免长时间误杀。
- `min_interval_seconds=15` 防止同一个账号在极短时间内被重复延长冷却。

如果同一账号在 30 分钟内反复触发 3 次以上，可把冷却升级到 5 分钟或更长。

## 计费口径

需要在后台和工单回复中区分三种情况：

| 情况 | 用户最终结果 | 是否计费 | 说明 |
| --- | --- | --- | --- |
| 上游直接失败，最终返回 `502/503/504` | 失败 | 不计费 | 不应写入成功 `usage_logs` |
| 上游 A 失败，切到上游 B 成功 | 成功 | 计费 | `ops_error_logs` 记录恢复前错误，`usage_logs` 记录最终成功 |
| 流式已输出后中断 | 部分输出/中断 | 按实际记录策略处理 | 不安全切号，需要单独审计是否有完整 usage |

工单解释建议：

> 失败的 `502` 请求本身未计费；当系统自动切换到其他上游并最终成功返回时，会按成功请求计费。后台错误日志中的 `Recovered upstream error` 表示中间上游失败已被恢复，不等于最终请求失败。

主要关注以下位置：

| 文件 | 关注点 |

## 验收用例

需要补充或更新测试：

- passthrough 上游返回 `502` 时，响应未开始写出，应触发 `UpstreamFailoverError`。
- passthrough 上游返回 `503` 时，应触发切号。
- passthrough 上游返回 `504` 时，应触发切号。
- `429`、`529` 保持现有切号行为。
- `400` 不触发切号。
- `401`、`403` 不纳入本次通用 5xx 切号策略。
- 流式响应已经开始输出后，不应切号到新账号。
- 切号成功后，`usage_logs.request_id` 使用 `client:<client_request_id>`，`ops_error_logs` 保留中间失败上游的 `request_id` 和同一个 `client_request_id`。
- failover 耗尽后才向用户返回 `502/503/504` 类错误。

## 后续可选优化

- 用户侧问题记录区分“最终失败”和“已重试成功的中间上游错误”。
- 后台错误日志默认聚合 `client_request_id`，避免把同一客户端请求的中间失败和最终成功割裂展示。
- 增加自动补偿辅助查询：只统计最终失败且无成功计费记录的请求；中间失败后成功的请求不纳入退款。

# OpenAI Pro / Plus 调度策略

## 目标

OpenAI 调度同时满足以下目标：

- `Codex Pro` 优先保证请求成功率、流完整性和首字体验。
- `Codex Plus` 在达到健康门槛后，优先使用有效倍率更低的上游。
- 保留会话粘性和池模式重试，减少上下文缓存分散。
- 账号、分组和模型状态严格隔离；用户请求什么模型就调用什么模型，不进行模型替换兜底。
- 自动切号只发生在响应尚未向用户输出之前。
- 用户错误中不暴露上游域名、账号名称、密钥或原始敏感响应。

## 有效倍率

调度、自动排序和后台展示必须使用同一套有效倍率：

1. 有 `manual_rate` 时使用 `manual_rate`。
2. 否则使用新鲜的上游探测倍率乘以 `rate_scale`。
3. 上游探测失败或过期时，倍率视为未知，不使用历史值参与低价排序。
4. 未绑定上游管理的账号，才允许使用明确配置且不等于数据库默认值 `1.0` 的账号倍率兜底。

例如账号 `#38842`：

```text
上游探测倍率 0.9 x rate_scale 0.1 = 有效倍率 0.09x
```

因此 `#38842` 应按 `0.09x` 参与排序，不能按 `0.9x` 处理。

## 分组策略

### Codex Pro

排序顺序：

1. 硬性可调度条件。
2. 账号与请求模型的健康状态。
3. 现有会话和缓存粘性。
4. 上游尝试成功率、流完整率、P95 首字和负载余量。
5. 体验接近时才使用有效倍率决胜。

建议健康门槛：

- 至少 `20` 次账号模型级样本后再升为主力。
- 上游尝试成功率原则上不低于 `95%`。
- 流式中断率原则上不高于 `2%`。
- P95 首字原则上不高于 `25s`。
- 主账号达到约 `80%` 并发或健康降级时，只把新会话切到备用账号；已有健康会话保持粘性。

Pro 至少保留两个稳定资源作为独立主力和热备。没有分组容量预留能力时，Pro 核心账号不同时作为 Plus 主力，避免 Plus 占满 Pro 并发。

### Codex Plus

排序顺序：

1. 硬性可调度条件。
2. 账号与请求模型的健康状态。
3. 新鲜、可信的有效倍率，从低到高排序。
4. 倍率相同时，比较首字、流完整率和负载。

建议健康门槛：

- 至少 `20` 次账号模型级样本后再升为主力。
- 上游尝试成功率原则上不低于 `90%`。
- 流式中断率原则上不高于 `5%`。
- P95 首字原则上不高于 `30s`。
- 未知倍率账号排在所有已验证倍率账号之后，不把旧倍率当作当前成本。

Plus 允许在 Pro 有容量余量时使用 Pro 备用资源，但不能抢占 Pro 主力。按当前售价倍率估算，`0.09x` 上游用于 `0.2x` Plus 的账面毛差约为 `55%`；失败重试和上游异常计费仍需从实际毛利中扣除。

## 选择与切号

- 每个“分组 + 精确模型”集中使用一个主账号，并保留有序备用账号。
- `Top-K=1` 只控制首选范围，不得删除同分组的请求级备用候选。
- 首选账号健康且有并发时，请求继续集中在首选账号，避免轮询打散缓存。
- 首选账号已满、调度快照过期、数据库复核失败或请求前发生可重试错误时，顺序尝试同分组同模型备用账号。
- 单次选择最多检查 `64` 个候选，防止异常大账号池产生无界数据库复核和并发槽请求。
- 池模式同账号重试预算保持不变；用完后才切换账号。
- 已向客户端输出 SSE 后不跨账号重试，避免拼接两个不一致的响应流。

## 健康和恢复范围

- `401`、凭证失效、余额不足、到期、手工停用属于账号级硬阻断。
- `429`、明确过载和代理隔离不允许被最后候选机制绕过。
- 明确模型不支持应记录为“账号 + 模型”硬状态并立即迁移；临时 `502/503/504/524` 和超时按“账号 + 模型”连续失败计数，不应误伤同账号的其他模型。
- 探针成功后恢复对应模型，不等待固定冷却时间结束。
- 最后候选只允许绕过与其持久化 transient 冷却匹配的账号级运行时镜像，不绕过模型冷却和任何硬阻断。
- 所有候选始终限定在用户当前分组，禁止跨分组兜底。

## 排名稳定性

- 新账号或新模型样本不足时作为候选，不直接升为主力。
- 使用 5 分钟短窗口发现故障，30 分钟窗口进行稳定排序。
- 候选连续多个窗口明显优于当前主力后再换位，避免倍率小幅变化或单次探针导致频繁抖动。
- 已有健康粘性会话不因其他请求的一次慢响应被拆除。临时故障第 1、2 次只让当前 HTTP/WS 请求切号并分别短冷却 10 秒，session 与 `previous_response_id` 原绑定不变；第 3 次连续失败冷却 45 秒并允许成功的备用账号接管。鉴权失效、余额不足和明确不支持模型不等待阈值，立即允许迁移。

## 验收条件

- `0.9` 上游倍率配合 `rate_scale=0.1`，所有调度路径均得到 `0.09`。
- `Top-K=1` 时，首选账号健康则持续集中；首选已满或复核失败时可选择同组第二账号。
- 同一账号的一个模型进入 transient 冷却，不影响其他模型。
- 最后候选可以使用匹配的 transient 账号冷却，但不能绕过 429、过载、模型限流、余额、认证、过期、手工停用或代理隔离。
- 粘性会话健康时保持原账号。
- 池模式重试次数和同账号重试顺序保持不变。
- Pro 按体验排序，Plus/Lite 按健康门槛后的有效倍率排序。
- 用户错误不包含上游身份和原始敏感内容。

## Codex Max 事故记录（2026-08-06）

### 现象

`Codex Max` 在北京时间 `14:36` 至 `14:40` 出现集中不可用。受影响请求主要是
`gpt-5.6-sol`：调度最终返回“当前分组不可用”，而不是模型不支持或用户权限错误。

检查时的分组绑定有 `#38896`、`#38898`、`#38842` 三个账号；其中 `#38842` 在
`14:41` 才绑定进该分组。故障窗口内，前两个账号发生了以下叠加：

1. `#38896` 的一分钟探针响应头超时，进入临时不可调度状态。
2. `#38898` 对 `gpt-5.6-sol` 连续收到上游 `502`，进入模型级运行时冷却。
3. 当时没有第三个可用备用账号，调度日志表现为 `pool=1, runtime_blocked=1`，于是返回 `503`。

这说明问题发生在账号可用性和上游质量层，不是用户访问凭证、分组授权或模型白名单的单点配置错误。

### 模型结论

以下为排查快照的近 6 小时最终请求结果，失败重试中的中间上游错误不重复计为成功：

| 模型 | 成功 | 用户可见失败 | 结论 |
| --- | ---: | ---: | --- |
| `gpt-5.6-terra` | 56 | 1 | 可继续提供 |
| `gpt-5.5` | 73 | 17 | 可用但需观察 |
| `gpt-5.6-sol` | 120 | 202 | 间歇性上游 `502` 和响应头超时，不能视为稳定资源 |
| `gpt-5.6-luna` | 0 | 68 | 当前没有健康资源，不能继续对外宣称可用 |

故障后仍可见 `gpt-5.6-sol` 的成功请求，说明不是持续性全站故障；但三家上游均出现
过 `502` 或超时，用户体验仍不满足 Max 分组标准。

### 处置原则

1. 未通过至少两个独立账号验证的模型不得展示在 Max 分组；当前应优先暂停
   `gpt-5.6-luna`，不允许改路由到其他模型。
2. Max 的首选账号必须来自最新探针和真实请求均健康的资源；退化资源只作为同模型备用，
   不得成为首选。
3. 账号模型级故障只隔离该模型；同账号的 `Terra`、`5.5` 等健康模型仍可被调度。
4. 发生全候选失败时返回统一的临时服务不可用错误，不暴露账号、上游域名或原始错误。
5. 调度修复已于 `2026-08-06 16:00`（北京时间）部署，提交为 `ba80a857a`。
   部署前已通过定向测试、完整前端构建、`embed` 后端构建和独立端口烟测，并通过
   同文件系统原子替换上线。上线后的首批 Codex Max 流量已同时在三个可调度账号上
   成功完成，观察窗口内未再出现该分组的 `account_select_failed`。
